# Asset License and Provenance Policy

## Hard boundary

`assets/approved_cc0/` is reserved for assets licensed **CC0 1.0 Universal** with evidence that the specific downloaded source file is covered. This is a strict library boundary, not an aspiration.

“Free,” “royalty-free,” “commercial use allowed,” “free with attribution,” “personal and commercial use,” and “generated by a free plan” do not meet the CC0 admission rule.

## Three provenance classes and five storage lanes

Every asset record must first declare one provenance class. This is separate from its technical state, where it is stored, and which game may use it.

| Provenance class | Meaning | May be a shared binary asset? |
| --- | --- | --- |
| `borrowed_library` | Third-party source that has recorded rights allowing this library to retain and redistribute it. | Yes, only under its verified rights. |
| `our_build` | Work authored by this team, including a modification or combination of recorded borrowed inputs. | Yes, subject to its own recorded license and input lineage. |
| `restricted_external` | Another party’s proprietary work used, evaluated, or licensed for a specific purpose without general redistribution rights. | No, unless the exact permission record says otherwise. |

The following filesystem lanes implement those classes and their review states:

| Lane | May contain binary source files? | Runtime eligible? | Required record |
| --- | --- | --- | --- |
| `approved_cc0` | Yes | Yes, after project-level review | Complete CC0 ledger entry and captured license evidence |
| `library_authored` | Yes | Yes, after project-level review | `our_build` creation record, ownership/license, borrowed-input lineage, author, project affinity, source-control revision, technical and visual review state |
| `candidates_needing_review` | Optional, preferably archive only | No | Source URL, reason for review, status |
| `generated_reference_only` | No final source asset by default | No | Tool, creation ID, terms, prompt/input provenance, review state |
| `paid_reference_only` | No vendor/proprietary source files unless redistribution is explicitly granted | No | `restricted_external` owner/source, purchaser or licensee where applicable, permitted projects, prohibited redistribution notes |

## Required proof for approval

Every approved entry must state:

1. Exact source page and creator/publisher.
2. Exact upstream archive filename and SHA-256 after download.
3. Exact internal source path(s) admitted from that archive.
4. License identifier: `CC0-1.0`.
5. License URL and a locally captured upstream license note in `licenses/upstream/`.
6. Retrieval date and reviewer.
7. Confirmation that commercial use and redistribution are permitted.
8. Technical intake result: import format, units, pivot, collision, material count, texture footprint, LOD state, and visual semantics.
9. Destination and use tags.

Missing evidence means `candidate`, never `approved`.

## Library-authored and project-specific packs

The shared library is allowed to contain our builds, including assets made for a particular game: character doll bases, rigs, clothing modules, portraits, setpieces, and effects. These assets are not made neutral by omission; their metadata must declare:

1. whether the pack is `shared`, `project_specific`, or `reference_only`;
2. a project-affinity identifier when it is project-specific;
3. provenance class, author/rights holder, creation method, applicable license, redistribution scope, and borrowed-input lineage where relevant;
4. literal subject and intended presentation;
5. style and body/rig metadata when the asset is a character pack;
6. adult-only status for any adult character presentation; and
7. consumer-engine review state separately for every consuming project.

Project affinity makes a result searchable and honest; it does not define ownership. A Pirate Island heroine base can therefore live in this repository as a labeled `our_build`, while DR Companion remains free to ignore it or to adopt it only when its rights and visual review permit.

## Project-specific derivatives

CC0 raw assets may be transformed for each game. Each project retains its own transformed file, manifest entry, source link, and visual review. Do not write project-specific culture, race, named-place, or character metadata into a *neutral third-party source entry*. Put that information in a scoped adapter or authored-pack record instead.

## Generated and paid sources

Generated outputs are not assumed CC0. They remain reference-only until their applicable tool terms, input provenance, and project admission are recorded. Third-party proprietary material—including paid store assets—is `restricted_external` by default. Record its constraints, but do not upload vendor source files merely because one contributor purchased or used them.

## License conflicts

When a source page, archive, embedded README, and marketplace listing disagree, treat the asset as quarantined. Preserve the evidence and resolve the conflict before any technical work or redistribution.

## Removal and correction

If later evidence invalidates an approval, immediately change the ledger status to `quarantined`, remove it from consuming project manifests, and record the reason. Do not rewrite history or silently delete the provenance record.
